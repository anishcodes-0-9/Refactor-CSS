# ADR-001 — Refactor-CSS v0.1 Architecture

Status: **proposed** · supersedes nothing · condenses `docs/architecture-review.md`
Date: 2026-08-24 · Rev 3 (B16 added — known runtime-generated selector namespaces — following review of historical research; see `docs/research-origin.md`)

Scope: binding contract for v0.1. Anything not listed under §1–§6 is **not binding** — see §8.

---

## 1. Binding decisions

Each is either expensive to reverse or safety-critical. Changing one requires a new ADR.

| # | Decision | Why it is binding |
| --- | --- | --- |
| **B1** | **The repository itself is the single publishable package.** No `packages/` directory, no `pnpm-workspace.yaml`, no workspace protocol. `src/`, `test/`, `package.json`, `tsconfig.json` sit at repo root. One `package.json`, one version, one `bin`, library and CLI exported from the same package. If a genuinely independent second package is needed later, introduce a workspace via a **new ADR** — do not pre-build the seam. | A pnpm workspace with a single member is a boundary paid for and not used. We already rejected premature package *splitting* (7 packages → 1); a workspace of 1 is the same mistake at a different layer. Flat-repo-as-package is the smallest structure that is still a real, publishable npm package. |
| **B2** | **Five domain types** (§3). `src/domain/` imports nothing internal and has **zero runtime dependencies**. | Makes every parser choice swappable and every extension a no-op on the model. Enforced by lint. |
| **B3** | **Index, not graph.** The selector↔consumer relation is `Map<key, SelectorRecord>`. | A graph invites traversal infrastructure nothing queries. Revisit only for route/fan-out analysis. |
| **B4** | **The join key is the normalized class-name string, and a key may resolve to multiple definitions.** `SelectorRecord.definitions` is `SelectorDefinition[]`, preserving every definition site — analysis never collapses same-key definitions into one, and duplication never blocks analysis. When `definitions.length > 1`, emit `duplicate-selector-definition` as an **info-level diagnostic and cascade-complexity signal**, and every finding for that key carries a caveat naming all definition sites. | The join key is still the central simplification, but silently collapsing distinct definitions would destroy provenance (B11 requires findings to cite *where*) and could hide a real cascade conflict rather than surface it. Preserving all definitions keeps the selector analyzable and keeps the uncertainty visible instead of erasing it. |
| **B5** | **Evidence has two orthogonal axes: `kind` × `resolution`** (§4). No `INFERRED` kind. | One enum cannot express "in source *and* dynamic". `INFERRED` would let conclusions feed conclusions. |
| **B6** | **Unresolved references are repository-wide sinks, not per-selector facts** (§4.3). Pattern sinks attenuate matching keys; opaque sinks **cap risk and add caveats, never suppress findings**. | This *is* "absence of evidence ≠ evidence of absence", mechanized. The single most important decision here. |
| **B7** | **Risk is a function of `(selector, operation)`.** `Operation = 'DELETE' \| 'RENAME' \| 'MOVE'`. | A single risk field will eventually be read as clearance for an operation it was not computed for. |
| **B8** | **`SAFE` is unreachable in v0.1.** Emittable set is `SAFE_WITH_VALIDATION \| REVIEW \| BLOCKED`. Every `BLOCKED` carries a `reasonCode`. | Static analysis cannot prove safety. An emittable-but-unemitted value is an attractive nuisance. |
| **B9** | **Three classification facets**: `referenceStatus`, `nature`, `ownership`. No `UNUSED` value exists in any enum. | Facets are independently derivable from distinct inputs; a combined enum forces lossy choices. |
| **B10** | **`nature` is computed from the CSS AST alone.** Element / `:root` / `body` / id / attribute / keyframe selectors are **structurally excluded** from findings. | Makes "never delete `body {}`" a type-level fact, not a rule someone can relax. |
| **B11** | **"Unused candidate" is a `Finding`, never a classification.** Findings assert something about the world and therefore require preconditions + mandatory non-empty `caveats`. | Classifications describe observations; only findings can be wrong in a way that costs a user their styles. |
| **B12** | **No numeric confidence anywhere** — not in the model, not in the JSON, not in the terminal output. | Fabricated calibration; invites `--confidence 0.95 --delete`; unarguable; does not compose. |
| **B13** | **Extractors are pure `(path, content) => { records, diagnostics }`.** ASTs are discarded immediately after extraction; every record carries `file` + content hash. | The one performance decision that is a full rewrite if deferred. Also unlocks workers and caching later. |
| **B14** | **The unit of analysis is the repository root.** Nothing is ever declared unreferenced on the basis of a subtree. | Makes monorepos correct with zero monorepo-specific code; expensive to retrofit. |
| **B15** | **CSS Modules (`*.module.{css,scss}`) get namespaced keys and are excluded from findings** in v0.1, with the count reported in coverage. Report JSON is **deterministic and carries `schemaVersion`**. | Unhandled, module `.hero` silently merges with global `.hero` and corrupts output on most real repos. Determinism makes tests sane and `--compare` trivial. |
| **B16** | **A known/configured runtime-generated selector namespace may only *attenuate* a recommendation, never *establish* usage.** Matching a namespace (e.g. a UI library's generated-class prefix) creates no `Evidence` and never changes `referenceStatus` — a match is not proof of a consumer. What a match *does* do, as a standing guarantee that must hold for every current and future rule: (1) `DELETE` risk on the matched selector is never more permissive than `REVIEW`, regardless of what any future rule would otherwise compute, until stronger (exact) evidence exists; (2) the finding carries a mandatory caveat stating the selector's true consumer may be generated by a library or runtime rather than authored in JSX/CSS-visible source. Namespace matching is a **generic, pluggable mechanism** — no vendor (MUI or otherwise) is hardcoded into the core engine. The configuration format and any initial namespace list are **unspecified in v0.1** (§8.2) — B16 binds the behavioral contract above, not an implementation. | A real, observed production false positive: library-generated override classes (e.g. MUI's `.Mui*` selectors), styled in the application's own stylesheet with zero JSX `className` evidence anywhere, would otherwise pass every precondition of `unreferenced-selector` and reach a confident delete recommendation — see `docs/research-origin.md`. A naming/namespace signal is exactly the kind of evidence B5/B9/B11 already forbid from creating positive usage, so protection must work by narrowing what a finding is *allowed to recommend*, never by fabricating evidence it doesn't have. |

## 3. The five domain types

`src/domain/index.ts` — complete and implementation-ready.

```ts
export const SCHEMA_VERSION = 1 as const;

/* ── supporting unions ────────────────────────────────────────────────── */

export type Resolution = 'exact' | 'pattern' | 'opaque';

export type EvidenceKind =
  | 'css-selector-definition'
  | 'jsx-class-attribute'
  | 'class-utility-call'      // clsx / classnames / cn / cx
  | 'dom-api-call'            // querySelector, classList.add, closest, matches, ...
  | 'html-literal'            // class="..." inside a string/template literal
  | 'html-injection'          // dangerouslySetInnerHTML, .innerHTML =
  | 'config-protected'
  | 'css-annotation'          // /* refactor-css-protect: reason */
  | (string & {});            // open: new extractors add kinds without a domain change

export type SelectorNature =
  | 'CLASS'                   // .card
  | 'CLASS_CONTEXTUAL'        // .checkout .card  — class, but part of a compound/descendant
  | 'ELEMENT'                 // h1, p, ul
  | 'GLOBAL_ROOT'             // html, body, :root, *
  | 'ID'                      // #main
  | 'ATTRIBUTE'               // [data-state="open"]
  | 'KEYFRAMES'
  | 'CUSTOM_PROPERTY';        // --brand-color

export type Ownership =
  | 'APPLICATION' | 'DESIGN_SYSTEM' | 'THIRD_PARTY' | 'GENERATED' | 'UNKNOWN';

export type ReferenceStatus =
  | 'REFERENCED'              // >=1 evidence with resolution 'exact'
  | 'REFERENCED_DYNAMICALLY'  // 0 exact, but >=1 matching pattern sink
  | 'UNREFERENCED';           // 0 exact, 0 matching pattern sink   <- NOT "unused" (B9)

export type Operation = 'DELETE' | 'RENAME' | 'MOVE';

/** B8: 'SAFE' exists for forward-compat but is never emitted in v0.1. */
export type Risk = 'SAFE' | 'SAFE_WITH_VALIDATION' | 'REVIEW' | 'BLOCKED';

export type BlockReason =
  | 'BLOCKED_THIRD_PARTY_OWNERSHIP'
  | 'BLOCKED_GENERATED_SOURCE'
  | 'BLOCKED_HTML_INJECTION_SINK'
  | 'BLOCKED_PROTECTED_BY_CONFIG'
  | 'BLOCKED_PROTECTED_BY_ANNOTATION'
  | 'BLOCKED_GLOBAL_SELECTOR_NATURE'
  | 'BLOCKED_DUPLICATE_DEFINITION';

/* ── 1. SourceLocation — the backbone ─────────────────────────────────── */

export interface SourceLocation {
  file: string;          // repo-relative, POSIX separators, ALWAYS
  line: number;          // 1-based
  column: number;        // 1-based
  endLine?: number;
  endColumn?: number;
}

/* ── 2. SelectorDefinition — a class name as defined in CSS ───────────── */

export interface SelectorDefinition {
  key: string;                       // normalized class name — THE JOIN KEY (B4)
  rawSelector: string;               // ".checkout .card:hover"
  nature: SelectorNature;            // from CSS AST alone (B10)
  scope: 'global' | 'css-module';    // B15
  loc: SourceLocation;
  stylesheet: string;                // repo-relative path
  ownership: Ownership;
  contentHash: string;               // B13
}

/* ── 3. Evidence — a place in source that references a class ──────────── */

export interface Evidence {
  key: string | null;      // null iff resolution === 'opaque'
  kind: EvidenceKind;      // WHERE it came from
  resolution: Resolution;  // HOW certain the value is
  loc: SourceLocation;
  snippet: string;         // literal source text, for the report
  extractor: string;       // which extractor produced it
  pattern?: string;        // required iff resolution === 'pattern', e.g. "button-*"
}

/* ── 4. Diagnostic — what we could not understand ─────────────────────── */

export interface Diagnostic {
  severity: 'error' | 'warning' | 'info';
  code: string;            // stable, greppable, documented
  message: string;
  loc?: SourceLocation;
}

/* ── 5. Finding — an assertion about the world ────────────────────────── */

export interface Finding {
  rule: string;            // "unreferenced-selector"
  key: string;
  operation: Operation;    // B7: risk is per-operation
  risk: Risk;
  reasonCode?: BlockReason;// REQUIRED when risk === 'BLOCKED' (B8)
  evidence: Evidence[];    // why we believe this — never empty
  caveats: string[];       // why we might be wrong — never empty (B11)
}
```

**There is no `Sink` type.** A sink *is* an `Evidence` with `resolution !== 'exact'`, indexed repository-wide instead of against a key. Introducing a sixth type would duplicate the model.

Two **container** types — not domain concepts, defined in their own modules:

```ts
// src/index/types.ts — derived, module-local
export interface SelectorRecord {
  key: string;
  definitions: SelectorDefinition[];   // B4: ALL definition sites, never collapsed.
                                        // length > 1 => duplicate-selector-definition diagnostic
  references: Evidence[];              // resolution === 'exact' only
  dynamicMatches: Evidence[];          // pattern sinks whose glob matches this key
  referenceStatus: ReferenceStatus;
}

// src/report/types.ts — the versioned wire format
export interface Report {
  schemaVersion: typeof SCHEMA_VERSION;
  tool: { name: string; version: string };
  root: string;
  coverage: Coverage;
  selectors: SelectorRecord[];   // sorted by key
  findings: Finding[];           // sorted by (risk, key)
  diagnostics: Diagnostic[];     // sorted by (file, line, code)
}

export interface Coverage {
  filesScanned: number;
  filesByKind: Record<string, number>;
  filesFailed: number;
  cssModuleSelectorsExcluded: number;
  globalOrElementSelectorsExcluded: number;
  duplicateDefinitionKeys: number;      // B4: count of keys with definitions.length > 1
  opaqueSinks: number;
  patternSinks: number;
  durationMs: number;
}
```

`Coverage` is passed **into** `rules/`, which is permitted to weaken its own conclusions based on it. That is how B6 is enforced mechanically rather than by convention.

## 4. Evidence: kind × resolution × sinks

### 4.1 The two axes

`kind` answers *where did this come from* (extractor-owned, open union).
`resolution` answers *how certain is the value* (closed, three values).

They are independent. `` className={`btn-${v}`} `` is `kind: 'jsx-class-attribute'` **and** `resolution: 'pattern'` — inexpressible with the single 8-value enum this replaces.

Consequences: `DYNAMIC` is not a kind, it is `resolution !== 'exact'`. `CMS` is not a kind, it is ownership + an `html-injection` sink. `THIRD_PARTY` is not a kind, it is `Ownership`. `RUNTIME` becomes a future `kind` with `resolution: 'exact'` and needs zero model change — that is the test that this model is right.

### 4.2 Extraction table (v0.1, exhaustive)

| Source construct | Result |
| --- | --- |
| `className="hero"` | `exact` × 1 |
| `className="a b"` | `exact` × 2 |
| `className={c ? "a" : "b"}` | `exact` × 2 (walk both branches) |
| `className={c && "a"}` | `exact` × 1 |
| `clsx("btn", on && "on")` | `exact` × 2 — string-literal args only; callee in `{clsx, classnames, cn, cx}` (configurable) |
| `` className={`btn-${v}`} `` | **pattern sink** `btn-*` |
| `` className={`btn ${v}`} `` | `exact` "btn" + **opaque sink** |
| `className={props.cls}` | **opaque sink** |
| `dangerouslySetInnerHTML` / `.innerHTML =` | **opaque sink**, `kind: 'html-injection'` |
| `querySelector(".modal .close")` | `exact` × 2 — arg parsed with the *same* selector parser as CSS |
| `classList.add("active")` | `exact` × 1 |
| non-literal arg to any supported DOM API | **opaque sink** |
| `className={styles.hero}` | CSS-module reference — indexed under namespaced key, excluded from findings (B15) |
| SCSS `#{$x}-title` | diagnostic + **pattern sink** |
| SCSS `&__title` | resolved via parent chain → `exact` definition key `card__title` |

Supported DOM APIs, fixed list: `querySelector` · `querySelectorAll` · `closest` · `matches` · `getElementsByClassName` · `classList.{add,remove,toggle,contains,replace}`.

**Not attempted:** type-directed resolution (`variant: 'a'|'b'`), constant propagation, cross-module data flow, any interprocedural analysis. Declining costs precision, not correctness — that is what the sink model buys.

### 4.3 Sink semantics (B6)

Sinks cannot attach to a key, because we do not know which key they mean. They live repository-wide.

**Pattern sink** (`btn-*`) — *targeted*. During indexing, any key matching the glob flips `UNREFERENCED → REFERENCED_DYNAMICALLY`, citing the sink as evidence. Precise, mechanical, no risk change needed.

**Opaque sink** (`className={props.cls}`, `html-injection`) — could match anything.

- ✗ Does **not** suppress findings. Every real repo has at least one; a silent tool is a useless tool.
- ✓ Every `unreferenced-selector` finding gains a caveat naming the sink count and locations.
- ✓ `DELETE` risk is **capped at `REVIEW`** repository-wide while any opaque sink exists.
- ✓ Any `html-injection` sink forces every `DELETE` finding to `BLOCKED / BLOCKED_HTML_INJECTION_SINK`.
- ✓ Counted prominently in `Coverage`.

One generic `html-injection` sink covers Contentful, Sanity, WordPress, Strapi, and every backend template — **without the tool knowing any of them exist.** Model the mechanism, not the vendors.

### 4.4 The only v0.1 rule

```
rule: unreferenced-selector
  requires  referenceStatus === 'UNREFERENCED'
  requires  nature === 'CLASS'                    (never CONTEXTUAL/ELEMENT/GLOBAL_ROOT/ID/...)
  requires  ownership === 'APPLICATION'
  requires  scope === 'global'
  requires  key not matched by config.protectedSelectors
  requires  no css-annotation protect on the rule
  emits     operation : 'DELETE'
            risk      : 'REVIEW'   ('BLOCKED' if any html-injection sink exists)
                        (never better than 'REVIEW' if key matches a known/protected
                         runtime-generated namespace — B16, regardless of any other input)
            caveats   : [ "<n> opaque class sinks exist in this repository: <locs>",
                          "runtime, CMS, and backend-template consumers are not analyzed" ]
                        + "defined in <n> places: <locs>"  when definitions.length > 1  (B4)
                        + "this selector matches the known/protected namespace <ns>; its
                           consumer may be generated by a library or runtime rather than
                           authored in source"  when key matches a namespace (B16)
```

`single-consumer-selector` is deferred — see §8, open question O3.

### 4.5 Known/protected runtime-generated namespaces (B16)

A namespace match is **not evidence** — it never creates an `Evidence` record and never moves `referenceStatus` off `UNREFERENCED`. It is a second, independent input to risk/caveat computation, structurally parallel to sink attenuation (§4.3) but sourced from configuration rather than extracted from source:

| | Sinks (§4.3, B6) | Namespaces (§4.5, B16) |
| --- | --- | --- |
| Source | Extracted from source code (a real construct the extractor saw) | Declared in configuration (a pattern the user or a future default list asserts) |
| Can create `Evidence`? | Yes — pattern sinks upgrade `referenceStatus` | Never |
| Effect on risk | Caps `DELETE` at `REVIEW`; `html-injection` forces `BLOCKED` | Caps `DELETE` at `REVIEW` (never more permissive) |
| Effect on caveats | Mandatory | Mandatory |

This is deliberately a **floor, not a ceiling** — a namespace match can never make a finding *more* dangerous than the rule would otherwise compute, and can never suppress a finding outright (that remains `config.protectedSelectors`' job, which excludes a key from the rule entirely — see §4.4's preconditions). B16 exists specifically for the case in between: a selector the tool has no positive evidence for, but also has principled reason not to recommend deleting with confidence.

The namespace list itself, and how it's configured, are **not specified in v0.1** — see §8.2. No specific library (MUI or otherwise) is named in the core engine; the mechanism is generic pattern-matching against a list that is empty by default.

## 5. v0.1 invariants (executable safety contract)

`test/invariants.test.ts` runs these across **every** fixture. **Write them before writing `rules/`.**

```
I1  No finding is ever emitted with risk === 'SAFE'.
I2  No selector whose nature is not 'CLASS' ever produces an unreferenced-selector finding.
I3  If any opaque sink exists, no DELETE finding has risk better than 'REVIEW'.
I4  If any html-injection sink exists, every DELETE finding is 'BLOCKED'.
I5  Every finding with risk === 'BLOCKED' has a reasonCode.
I6  Every finding has non-empty evidence[], and every SourceLocation resolves to a
    real file/line/column in the fixture.
I7  Every unreferenced-selector finding has at least one caveat.
I8  Running analyze twice on the same input produces byte-identical JSON.
I9  Every Evidence with resolution 'exact' traces to a construct in the §4.2 table.
    (No exact evidence is ever synthesized for an unsupported construct.)
I10 Every Evidence with resolution 'pattern' has a `pattern`; every 'opaque' has key === null.
I11 A key with definitions.length > 1 is never dropped, merged into one definition, or
    excluded from the index — it remains analyzable and produces a duplicate-selector-
    definition diagnostic. (B4)
I12 A key matching a configured/known runtime-generated namespace never receives a
    DELETE finding with risk better than 'REVIEW', and that finding always carries the
    namespace caveat — regardless of what any other rule input would otherwise permit.
    A namespace match is never the sole basis for `referenceStatus !== 'UNREFERENCED'`. (B16)
```

I2, I3, I4, I7 are the four that prevent the catastrophic false positive. I11 prevents the catastrophic silent-collapse. I12 prevents a heuristic from ever being read as evidence — it is currently vacuous against v0.1's single rule (which never exceeds `REVIEW` regardless, per B8) but binds every rule added after v0.1, including once `SAFE`/`SAFE_WITH_VALIDATION` become reachable.

### 5.1 Known untraced reachability paths (caveat catalogue)

The following are **known-incomplete** static-analysis boundaries — cases where a real consumer can exist through a path this analyzer does not trace. None of these expand v0.1's scope to trace them; each is instead a standing entry in the `unreferenced-selector` caveat vocabulary (§4.4), so an incomplete analysis is always disclosed rather than silently presented as complete:

| Path | Why it's untraced in v0.1 | Caveat text (illustrative) |
| --- | --- | --- |
| SCSS `@extend` | Reachability through Sass's compile-time inheritance graph, not the className-string join (B4/§4.2 already scopes SCSS to source-level, unevaluated) | "SCSS `@extend`/mixin-generated reachability is not traced — a selector may be a live `@extend` target with zero JSX evidence" |
| `:global(...)` inside a CSS Module | Crosses the module/global boundary (§13.4-equivalent, B15 scopes module selectors out of findings already; this covers a global selector referenced *from inside* a module partial) | "selectors referenced via `:global(...)` from a CSS Module are not traced" |
| Runtime-generated library classes | Covered structurally by B16 (§4.5) — namespace match, not a traced reachability path, but belongs in the same disclosure vocabulary | "this selector matches a known/protected runtime-generated namespace; see B16" |

This is a documentation/caveat-vocabulary addition only — **not** a commitment to build an SCSS dependency engine, a module-boundary tracer, or any new extractor in v0.1. `@extend`/`:global()` tracing remains explicitly out of scope (§4.2's SCSS limitations, unchanged); this section only ensures the *disclosure* is standardized rather than ad hoc.

## 9. One-paragraph summary

Build **one flat repository-as-package** around **five domain types** and a **string-keyed index that preserves every definition per key**. Evidence carries **two axes** (`kind` × `resolution`); anything not `exact` becomes a **repository-wide sink** that attenuates precisely (pattern) or caps risk and adds caveats (opaque) — that mechanism *is* the product thesis. A known/configured runtime-generated namespace works the same way from the other direction: it never fabricates evidence, only narrows what a finding may recommend (B16). Risk is per **(selector, operation)**, `SAFE` is unreachable, `BLOCKED` always cites a reason. `nature` from the CSS AST alone makes global and element selectors structurally undeletable. Duplicate definitions are surfaced as a diagnostic, never silently merged. **No numeric confidence, and no enum value named `UNUSED`.** Ship the M1 walking slice in week one, guard it with invariants I2/I3/I4/I7/I11/I12, and let real repositories decide everything in §8.
